# Formal-model decomposition

## Decision

Agentlog is verified with several small machines, not one universal proof
state:

```text
EventStoreModel
DispatcherModel
ModelLoopModel
ResourceModel
CompositionModel
```

The existing fixed `2/2` trace model remains an integration witness and runtime
refinement target.

## EventStoreModel

State contains stream/global histories and positions, subscription checkpoints,
and committed event identities.

It accepts `Append` and `CommitSubscriptionBatch` with expected stream version
and checkpoint inputs. It proves:

```text
append-only histories
monotonic stream/global positions
unique event identities
atomic event batches
atomic output-batch + checkpoint commits
conflicts leave state unchanged
checkpoint-only commits do not assert stream version
```

It does not execute reactions, effects, providers, or tools.

## DispatcherModel

It assumes the EventStore guarantees. State contains the durable checkpoint,
selected event, immutable computed output batch, terminal observation, commit
attempt, and process/crash state. Physical effect invocation is separate
operational state.

It proves:

```text
checkpoint monotonicity
restart from the durable checkpoint
commit retry reuses one immutable output batch
an already committed consumed event cannot append outputs again
fresh terminal recheck suppresses stale outputs
physical invocation is at-least-once
committed result is at-most-once per operation
```

It does not decide model-loop continuation policy.

The implemented `formal/crash_window` artifact currently proves only the
external-invocation slice of this model: stable operation identity across
crash/retry and at-most-one committed result. Checkpoint selection, immutable
output batches, terminal recheck, and their composition with EventStoreModel
remain future obligations. One controlled cancellation/restart scenario checks
that the real Python effect dispatcher refines this slice across five observed
operational boundaries; it is evidence, not universal refinement.

## ModelLoopModel

It assumes one deterministic policy evaluation per consumed event, atomic
ordered reaction batches, preserved effect operation identity, and valid
resources.

The concrete witness configuration is:

```text
MODEL_MAX_MODEL_STEPS = 2
MODEL_MAX_TOOL_CALLS  = 2
```

The parameterized model uses two independent `low | before | at` counter
classes with:

```text
low    → low | before
before → at
at     → at
```

This is a sound finite over-approximation for arbitrary positive limits, not an
exact quotient.

It proves request/result compatibility, operation preservation, single result
per request, independent counter updates, guard placement, atomic sibling
causation for `AnswerProduced`/`RunCompleted`, and terminal uniqueness.

## ResourceModel

State contains definition version, provider capability, captured tool-schema
fingerprints, and runtime registry fingerprints.

It proves definition immutability and that operational provider/tool resources
match the registered definition before invocation. It does not prove external
provider or tool correctness.

## CompositionModel

Local proofs are insufficient without interface obligations:

```text
Store.atomic_batch_checkpoint
→ dispatcher observes outputs and checkpoint together after restart

ModelLoop.atomic_reaction_outputs
→ dispatcher commits the ordered sibling batch without rewriting causation

Dispatcher.one_committed_processing_per_checkpoint
→ one request has at most one committed result

Resource.definition_matches
→ dispatcher may invoke the selected capability

ModelLoop.single_terminal
∧ Dispatcher.fresh_terminal_recheck
∧ Store.atomic_commit
→ terminal history is absorbing under modeled races
```

Crash composition explicitly permits repeated physical invocation after a
crash before commit. It guarantees stable operation identity and at-most-one
committed result, not exactly-once external execution.

## Integration trace model

The fixed trace model remains responsible for concrete counterexamples, exact
causation/operation positions, mutation sensitivity, and runtime/FastAPI
snapshot refinement:

```text
limits:             2/2
saturated states:   552
transitions:        1509
runtime ABI:        48 bytes at history <= 10
```

It does not replace the local proofs or prove arbitrary policy limits.

## Implementation order

```text
1. EventStoreModel + storage mutants
2. DispatcherModel + restart/crash mutants
3. ModelLoopModel + parameterized limit mutants
4. ResourceModel + fingerprint mutants
5. CompositionModel + interface mutants
6. fixed trace-model regression
7. per-layer runtime refinement
8. FastAPI integration refinement
```

Every formal transition relation is generated by FASM and checked through
setdb. Python may extract runtime observations for refinement; it does not
implement the formal transition systems.
