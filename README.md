# Как я проверял идеи советской кибернетики на языковых моделях, MCP и БД

Одними из самых полезных материалов по современным ИИ-агентам
для меня оказались книги по кибернетике времён СССР.

Инженеры того времени систематически работали с классом задач,
который сегодня снова возник вокруг агентных систем:

Технологии новые, а неопределённость прежняя: действие уже могло произойти, процесс мог умереть, наблюдение могло не сохраниться, но системе всё равно нужно определить, что считать фактом и что допустимо дальше.
Ненадёжный компонент — это большая языковая модель. Среда — программные интерфейсы, MCP-серверы, базы данных и объектные хранилища.

Я решил не ограничиваться исторической аналогией и собрал работающий эксперимент. Так появился [Agentlog](https://github.com/kroq86/agentlog) — основанная на событиях среда исполнения для durable-агентов на Python.

> Agentlog — durable runtime для bounded AI workflows, а не RAG- или MCP-платформа.

Один пример границы, которую он реально проверяет (`examples/bounded_corporate_agent/`, `docs/model-loop.md`):

```text
bounded model/provider
→ validated tool proposal
→ guarded transition
→ durable execution
→ goal-gated completion
```

Модель или детерминированный provider предлагает один вызов инструмента; всё, что происходит дальше — валидация, guard перехода, само исполнение, нормализация результата и допуск до завершения — управляется явным, детерминированным, durable-кодом. Reference example по умолчанию использует воспроизводимую заглушку, а флаг `--ollama` подключает реальную локальную модель через `OllamaProvider`.

### Текущая метка

> **Single-worker durable guarded execution framework candidate.**

- Подходит для controlled single-worker pilot — один effect-воркер на run,
  без координации между несколькими воркерами.
- Внешние side effects по-прежнему требуют downstream idempotency на стороне
  самого tool/интеграции. Внутри одного воркера at-most-one-committed-result —
  bounded/scenario-проверенное свойство (crash-window модель плюс отдельные
  восстановленные сценарии против реальных Ollama/MCP-крашей), а не
  exactly-once физическое исполнение.
- Multi-worker safety пока не заявляется.
- `EffectDispatchAttempt`/attempt ledger (`src/agentlog/attempts.py`) — это
  фундамент для будущего lease/claim protocol, а не сам lease protocol;
  несколько воркеров сейчас могут легитимно создать несколько физических
  попыток для одной операции.
- `RunAbstained` bounded model и attempt-telemetry сейчас в `## Unreleased` в
  `CHANGELOG.md`, а не в выпущенной `0.4.2`.
- Пять control event types (`GoalSatisfied`/`GoalNotSatisfied`/
  `WorkflowInvariantViolated`/`WorkflowCycleDetected`/`RunAbstained`) покрыты
  отдельными bounded-моделями с невакуозными witness'ами и targeted mutants;
  base trace/bisimulation reference-модель (`formal/model/spec.py`) для этих
  событий остаётся вакуозной, и composition между локальными моделями не
  установлена.

## Исторические координаты

[Дмитрий Поспелов в «Ситуационном управлении: теория и практика»](https://djvu.online/file/MKecX5GfcelgX) рассматривал управление сложными объектами, которые неудобно описывать одной жёсткой формальной моделью. Текущую ситуацию нужно представить, сопоставить с классом допустимых решений, выполнить переход и снова наблюдать объект.

[Михаил Цетлин в работе «О поведении конечных автоматов в случайной среде»](https://www.mathnet.ru/rus/at12417) исследовал автомат, получающий вероятностную реакцию среды на собственные действия. Более широкий корпус его работ собран в книге [«Исследования по теории автоматов и моделированию биологических систем»](https://libarch.nmu.org.ua/handle/GenofondUA/39075).

[Алексей Ивахненко в «Индуктивном методе самоорганизации моделей сложных систем»](https://www.gmdh.net/articles/theory/bookInductModel.pdf) строил системы, где модели-претенденты генерируются и отбираются по внешнему критерию. Это одна из исторических линий, близких к автоматизированному машинному обучению.

История [проектов Анатолия Китова](https://publications.hse.ru/view/365100728) и Виктора Глушкова, включая изложенные Глушковым [«Макроэкономические модели и принципы построения ОГАС»](https://djvu.online/file/e8TPQL3C5tIRJ), добавляет ещё одну координату: информационная система изменяет не только передачу данных, но и распределение контроля над решениями.

Вместе они задают точные инженерные вопросы:

```text
Что является наблюдаемой ситуацией?
Какое действие допустимо?
Что отвечает среда?
По какому внешнему критерию проверяется модель?
Кто владеет данными, действием и наблюдением результата?
```

## Почему простые объяснения дают сложную картину

Языковую модель, инструмент, повтор, артефакт, дочерний запуск, перезапуск, контрольную точку и причинность легко объяснить по отдельности. Но восемь простых сущностей заставляют читателя самостоятельно построить их декартово произведение. Даже если грубо оставить каждой координате только два состояния, получится 2^8 = 256 комбинаций. Это лишь иллюстрация комбинаторного роста: реальное пространство состояний увеличивается быстрее самого списка понятий.

Это ловушка: простой текст создаёт глобально сложную модель в голове.

Вместо этого определю один более сложный объект и один переход. Вызов модели, вызов инструмента и продвижение дочернего запуска окажутся его типизированными специализациями, а модель артефактов присоединится через границу результата инструмента.

Достаточно удерживать одну границу: что было предложено, что разрешено, что зафиксировано до внешнего действия, что физически произошло и что из произошедшего стало частью истории.

## Сложность не исчезает — она меняет форму

Для любого значения или события нужно ответить на несколько вопросов:

```text
Какой это тип операции?
Где оно находится относительно внешнего действия?
Имеет ли оно устойчивую идентичность?
Является ли оно предложением, запросом или наблюдением?
Стало ли оно фактом сохраняемой истории?
В каком причинном порядке оно находится?
Сколько физических попыток ему соответствует?
Как оно восстанавливается после перезапуска?
```

Тогда сложность представляется не плоским списком случаев, а типизированным пространством:

```text
операция
× стадия протокола
× идентичность
× статус фиксации
× причинный порядок
× порядок исполнения
× правило восстановления
```

Это пространство по-прежнему велико. Но большая часть его точек недопустима по построению:

```text
наблюдение без предшествующего запроса             запрещено
два итоговых результата с одним operation_id       запрещено
изменение идентичности промежуточным обработчиком   запрещено
продвижение после итогового состояния               запрещено
повтор с новым operation_id                         запрещён
незафиксированное наблюдение как источник истины    запрещено
```

Именно запреты уменьшают эффективную сложность. Система не перечисляет все возможные комбинации, а определяет генератор допустимых переходов и инварианты, отсекающие остальные.

Например, зафиксированный `ToolCallFailed` занимает вполне определённое место:

```text
тип операции:          инструмент
стадия:                после попытки внешнего исполнения
вид значения:          наблюдение
статус:                зафиксировано
идентичность:          operation_id сохранён
причинный порядок:     после ToolCallRequested
порядок исполнения:    после конкретной физической попытки
правило восстановления: второй итоговый результат запрещён
```

Незафиксированный результат после аварийного завершения имеет уже другие координаты:

```text
тип операции:          инструмент
стадия:                после возможного внешнего исполнения
вид значения:          мимолётное наблюдение
статус:                не зафиксировано
идентичность:          идентичность запроса известна
причинный порядок:     запрос существует
порядок исполнения:    физическая попытка могла состояться
порядок фиксации:      результата нет
правило восстановления: запрос разрешено повторить
```

Одна операционная семантика поэтому не является упрощённой картинкой всей программы. Это система координат и правил композиции:

```text
тип определяет форму запроса и наблюдения
идентичность связывает повторные физические попытки
история определяет принятые факты
проверка допустимости ограничивает переходы
граница внешнего действия отделяет решение от физического исполнения
граница фиксации отделяет физическое событие от знания системы
правило восстановления определяет продолжение после потери процесса
```

Вызов модели, вызов инструмента и дочерний запуск не становятся одинаковыми. Они используют одну грамматику перехода, но подставляют разные типы запросов, исходов, идентичностей и ограничений. Артефакт соединяется с этой грамматикой слабее: у него нет собственного сохраняемого события запроса, но он добавляет отдельную модель идентичности содержимого к результату операции.

Наивное описание требует удерживать произведение состояний подсистем. Факторизованное описание требует удерживать набор типов, переходов, инвариантов и правил композиции. Agentlog не уменьшает физическое пространство возможных сбоев. Он уменьшает число независимых правил, которыми это пространство приходится описывать.

> Сложность системы остаётся комбинаторной. Некомбинаторным становится её описание.

## Пространство не только большое — оно меняется во времени

Координаты описывают положение события, но система не остаётся в этом положении. Каждая фиксация не просто добавляет запись в историю. Она изменяет состояние и тем самым меняет множество допустимых следующих переходов.

```text
H_t
→ S_t = восстановить(D, H_t)
→ Допустимые(S_t)
→ зафиксировать(e_t)
→ H_{t+1}
→ S_{t+1} = восстановить(D, H_{t+1})
→ Допустимые(S_{t+1})
```

До `ToolCallRequested` вызов ещё можно сформировать. После фиксации запроса повторная попытка должна сохранять ту же `operation_id`. После итогового результата второй результат запрещён. После итогового состояния дальнейшее продвижение невозможно. В других местах фиксация, наоборот, открывает новый переход: завершение текущего дочернего запуска разрешает старт следующего.

Допустимость следующего шага определяется текущим состоянием, восстановленным из совместимого определения и зафиксированной истории. Множество допустимых следующих переходов не просто сужается: оно перестраивается после каждого принятого события.

Перезапуск не возвращает систему в исходную точку. Новый процесс получает совместимое определение, заново регистрирует рабочие ресурсы, восстанавливает текущее положение из истории и продолжает тот же протокол из уже достигнутой области пространства состояний.

Сложность возникает не только из числа комбинаций координат, но и из зависимости каждого следующего шага от пути, по которому система пришла в текущее состояние. Здесь важно различать четыре представления:

```text
пространство состояний
  какие состояния вообще представимы

система переходов
  какие пути между состояниями допустимы

история
  какой путь был принят системой и стал источником истины

рабочая трасса
  какие физические попытки происходили по дороге
```

История и рабочая трасса могут расходиться: одна принятая операция способна соответствовать нескольким физическим попыткам. Поэтому восстановление опирается на историю, а наблюдаемость повторов требует отдельной рабочей трассы.

> Координаты задают положение события. История задаёт принятую траекторию. Инварианты ограничивают не только точки, но и допустимые пути между ними.

Agentlog факторизует не только пространство состояний, но и описание эволюции системы во времени.

## Одна операционная семантика

Пусть конфигурация исполнения имеет вид

```text
X = (D, H, K, R)
```

где:

- `D` — неизменяемое определение: типы событий, инструменты, правила, шаблоны и определение последовательности;
- `H` — только дополняемая сохраняемая история;
- `K` — изменяемая сохраняемая контрольная точка;
- `R` — явно зарегистрированные рабочие ресурсы: поставщик модели, инструменты и переходники хранилищ.

Сохраняемые данные среды исполнения здесь — `H` и `K`, но их роли различаются: `H` является только дополняемым источником истины, а `K` — изменяемой рабочей контрольной точкой. Определение `D` должно оставаться совместимым с сохранённой историей, а ресурсы `R` регистрируются заново при запуске среды исполнения.

Состояние агента не является второй независимой истиной. Оно вычисляется из определения и истории:

```text
S = восстановить(D, H)
```

Внешний компонент выдаёт предложение `p`. Проверка допустимости интерпретирует его относительно состояния:

```text
G(S, p) → Отклонить(f) | Принять(q)
```

Здесь `G` обозначает совокупность проверок протокола, а не отдельный публичный класс Agentlog.

`q` — ещё не внешний вызов, а неизменяемый запрос: содержимое, `operation_id`, причинность и идентичность. Принятый запрос сначала попадает в историю:

```text
H1 = H + ЗапросЗафиксирован(q)
```

и только после этого диспетчер получает право пересечь границу среды:

```text
E_R(q) → o
```

`o` — рабочее наблюдение, но ещё не факт предметной истории. После проверки протокола и допустимого преобразования результата получается проверенный кандидат `c`. Затем среда исполнения фиксирует наблюдение и контрольную точку:

```text
зафиксировать(H1 + Наблюдение(q, c), K)
→ Успех(H2, K')
| ОшибкаФиксации(H1, K)
```

После успеха новое состояние снова вычисляется:

```text
S' = восстановить(D, H2)
```

Вся система сворачивается в:

```text
предложение p
→ проверка допустимости G(S,p)
→ зафиксированный запрос q
→ внешнее действие E(q)
→ рабочее наблюдение o
→ зафиксированное наблюдение c
→ проекция состояния S'
```

Эта цепочка задаёт только временной скелет. Полное положение события определяется координатами, введёнными выше: типом, идентичностью, статусом фиксации, порядками и правилом восстановления.

Это несущая конструкция Agentlog. Остальные механизмы не добавляют новые оси — они уточняют типы `q`, `E` и `c`.

У этой конструкции одновременно три разных порядка, и смешивать их нельзя.

```text
причинный порядок
  какое событие породило следующий запрос

порядок исполнения
  в какой последовательности реально выполнялись внешние попытки

порядок фиксации
  какие наблюдения и в какой последовательности стали фактами истории
```

В штатном сценарии три порядка выглядят почти одинаково, поэтому обычный тест легко создаёт иллюзию простой линейной программы. При повторной попытке и аварийном завершении они расходятся. Одна причинная идентичность может иметь несколько физических попыток исполнения, но не должна получить несколько конкурирующих зафиксированных результатов. Именно это расхождение делает событийную модель здесь не способом журналирования, а языком разделения физического мира и принятого системой знания о нём.

Есть и второе разделение: идентичность, содержимое и состояние не взаимозаменяемы. Промежуточному обработчику разрешено менять содержимое, но запрещено менять идентичность. Поставщик модели или инструмент создаёт наблюдение, но не назначает ему состояние зафиксированного факта. Контрольная точка ускоряет продолжение, но не заменяет историю. Каждое значение получает не просто место хранения, а набор допустимых преобразований; поэтому неверное присваивание оказывается нарушением протокола, а не странным поведением очередного переходника.

## Три специализации durable-перехода и связанная модель артефактов

```text
Модель
  запрос:       ModelCallRequested
  среда:        поставщик модели
  наблюдение:   ModelCallSucceeded
                ModelCallFailed
                ModelCallRejected
                ModelOutputRejected
  идентичность: event_id, operation_id, causation_id

Инструмент
  запрос:       ToolCallRequested
  среда:        инструмент или переходник MCP
  наблюдение:   ToolCallSucceeded
                ToolCallFailed
                ToolCallRejected
  идентичность: operation_id

Последовательность
  запрос:       ChildStartRequested
  среда:        среда исполнения дочернего запуска
  наблюдение:   ChildCompleted / ChildFailed
  идентичность: идентификатор дочернего запуска
```

Артефакты связаны с этим протоколом, но не являются четвёртой буквальной специализацией durable-границы запроса и результата.

`SQLiteArtifactStore.register_external()` не создаёт собственного события запроса в `EventStore`. `ArtifactModel` проверяет неизменность уже зарегистрированной идентичности артефакта, а связь с сохраняемым исполнением проходит через результат инструмента и проверяемые сценарии исполнения.

Теперь промежуточные обработчики, шаблоны, последовательность и перезапуск можно вывести из общей схемы, а модель артефактов присоединить через явную границу результата инструмента, не создавая для каждого механизма отдельную картину мира.

### Промежуточные обработчики сохраняют идентичность перехода

`before_model` и `before_tool` преобразуют содержимое до фиксации запроса; `after_model` и `after_tool` — наблюдение после внешнего вызова, но до фиксации результата:

```text
m_before: Содержимое → Содержимое
m_after:  Наблюдение → Наблюдение
```

Они могут менять значения, но не структурную идентичность:

```text
идентичность(m(x)) = идентичность(x)
```

Поэтому сохраняемое событие содержит фактически отправленное или принятое значение после всей цепи. Промежуточные версии не становятся отдельными предметными событиями: для перезапуска они не нужны, а автомат состояний не должен зависеть от деталей реализации промежуточных обработчиков.

### Разрешение инструкции канонизирует запрос

Шаблон `t`, привязки `b` и точные ссылки на артефакты `a` разрешаются до `ModelCallRequested`:

```text
разрешить(t, b, a) → i
```

Разрешённая инструкция `i` входит в `q`. После этого повторная попытка использует то же зафиксированное содержимое, а не выполняет разрешение заново относительно изменяемой среды:

```text
Повтор(q) → то же содержимое
```

Одна идентичность операции не может обозначать два разных фактических запроса. Контракт: [инструкции](docs/instructions.md), модель: [`formal/instructions`](formal/instructions/README.md).

### `ArtifactRef` фиксирует идентичность содержимого

Для встроенного артефакта SQLite хранит двоичные данные и метаданные. Для внешнего артефакта обязанности разделены:

```text
внешнее хранилище сохраняет точную версию объекта
→ переходник проверяет версию, хеш и размер
→ SQLiteArtifactStore регистрирует ArtifactRef
→ EventStore фиксирует результат операции
```

Модель артефактов не доказывает, что внешний объект — например, объект в MinIO — действительно соответствует заявленному хешу: это обязанность переходника. Модель доказывает неизменность зарегистрированной идентичности:

```text
одинаковые (имя, версия)
→ одинаковые (тип, хеш, размер, ссылка на хранилище)
```

Контракт: [артефакты](docs/artifacts.md), модель: [`formal/artifacts`](formal/artifacts/README.md).

### Последовательность композирует ту же границу запроса и результата

Дочерний запуск остаётся самостоятельным запуском с собственной историей. Родитель хранит запрос запуска, неизменяемую идентичность дочернего запуска и его итоговое наблюдение. Для текущего дочернего запуска `i`:

```text
Старт(i) → Итог(i) → Старт(i + 1)
```

Стрелка здесь означает порядок зафиксированных событий, а не физических попыток отправки. Отсюда следуют инварианты: не более одного активного дочернего запуска, монотонный индекс, неизменяемый идентификатор дочернего запуска, отсутствие повторного запуска завершённого дочернего запуска и завершение родителя только после последнего дочернего запуска.

Ветвления, циклы, параллелизм, компенсация и согласование не скрыты в параметрах этой модели. Для них потребуются другие переменные состояния и обязательства композиции. Контракт: [последовательность](docs/sequence.md), модель: [`formal/sequence`](formal/sequence/README.md).

## Окно аварийного завершения — не крайний случай, а следствие модели

Внешнее исполнение

```text
Исполнить(q)
```

и фиксация результата

```text
ЗафиксироватьНаблюдение(q, c)
```

не являются одной атомарной операцией:

```text
ToolCallRequested зафиксирован
→ внешний вызов завершён
→ процесс аварийно остановлен
→ ToolCallSucceeded не зафиксирован
```

После перезапуска среда исполнения видит `q`, но не `c`. Из отсутствия зафиксированного наблюдения невозможно вывести, произошло ли действие.

```text
обработка зафиксированного запроса: попытка может выполняться повторно
зафиксированный Результат(q):  не более одного раза
```

при этом

```text
operation_id(Повтор(q)) = operation_id(q)
```

При обработке зафиксированного запроса среда исполнения допускает повторную физическую попытку; зафиксированный результат существует не более чем в одном экземпляре на границе операции; идентичность повторной попытки не меняется.

Здесь особенно важно различать неопределённость мира и определённость протокола. После аварийного завершения среда исполнения не знает, состоялся ли внешний эффект, и не может восстановить это знание из локальной памяти процесса. Но она точно знает, какой запрос разрешено повторить, какую идентичность нельзя заменить и какой второй итоговый результат нельзя принять. Протокол не устраняет неопределённость; он ограничивает множество корректных действий внутри неё.

Поэтому гарантия строится не вокруг фантазии о выполнении «ровно один раз», а вокруг асимметрии двух контуров. Операционный контур допускает повтор, потому что среда могла принять запрос без подтверждения. Контур фиксации запрещает раздвоение принятого результата, потому что два итоговых наблюдения с одной идентичностью сделали бы дальнейшее состояние неоднозначным. Идемпотентность внешнего переходника уменьшает цену повтора, но не заменяет эту границу и не превращает физическое исполнение в транзакцию `EventStore`.

Для `save_report` первая попытка может выполнить запись в MinIO и завершиться до регистрации в SQLite. Новая среда исполнения повторяет операцию с детерминированным ключом объекта, проверяет точную версию, идемпотентно регистрирует ту же `ArtifactRef` и фиксирует один результат. Рабочий журнал вызовов при этом обязан сохранить обе попытки.

Модель: [`formal/crash_window`](formal/crash_window/README.md), контракт среды исполнения: [внешние действия](docs/effects.md).

## Память агента — это память протокола

Контекст языковой модели или векторная база данных отвечают на вопрос
«что полезно показать модели».
Память протокола отвечает на другой вопрос:

> Какая информация достаточна, чтобы после перезапуска определить допустимый следующий переход?

В конфигурации `X = (D, H, K, R)` определение должно иметь версию или оставаться совместимым; история является источником истины; контрольная точка восстанавливается или сверяется с историей; ресурсы заново предоставляет регистрация среды исполнения; наблюдение, не вошедшее в `H`, не может считаться зафиксированным фактом.

Поэтому определение, сохраняемая история, сохраняемая контрольная точка, рабочий ресурс, производное состояние и мимолётное наблюдение — не список возможностей, а разные классы информации с разными правилами восстановления. Ошибка возникает не из-за «недостаточной памяти вообще», а из-за помещения значения не в тот класс.

## Языковая модель предлагает действие, но не определяет семантику исполнения

Языковая модель может сформировать предложение, которое не соответствует ожидаемому продуктовому протоколу.
Некоторые нарушения блокируются до пересечения границы внешнего действия и завершают запуск отказом — например, несколько вызовов инструментов там, где разрешён только один.
Другие траектории могут формально завершиться `RunCompleted`, но быть отклонены отдельным продуктовым verifier. Текстовый псевдовызов инструмента относится именно к этому случаю.
Детерминированный поставщик модели остаётся эталоном приёмки выпуска. Ollama проверяет реальный транспорт и соблюдение ограничений, но надёжность планирования конкретной локальной модели не является условием выпуска. Подробности: [локальная лаборатория контроля качества](examples/local_qaqc/README.md).

## Управление полномочиями также является частью границы

Если идентичность действия и владение наблюдением входят в протокол, вопросы контроля нельзя полностью вынести в административное приложение:

```text
кто имеет право породить предложение
кто проверяет допустимость
кто владеет внешним ресурсом
кто принимает наблюдение
кто может объявить итоговое состояние
кто читает причинную историю
```

ОГАС здесь полезна не как готовая архитектура, а как напоминание: изменение информационного контура меняет распределение контроля.

Agentlog 0.3 эту модель управления полностью не реализует: авторизация для промышленной эксплуатации, утверждение человеком и распределённое владение полномочиями остаются вне текущей границы.

## Что именно проверено

Модель не доказывает интеллект, полезность или правдивость языковой модели. Она проверяет предикаты над системой переходов:

```text
Результат(q) требует ЗафиксированныйЗапрос(q)
ЗафиксированныйРезультат(q) возникает не более одного раза
ИтоговоеСостояние(S) запрещает дальнейшее продвижение
КонтрольнаяТочка не движется назад
Повтор(q) сохраняет идентичность
```

Для каждого существенного предиката есть намеренно испорченный вариант семантики. Неизменённый checker должен построить конкретный контрпример для нужного нарушения. Ошибка компиляции, превышение времени, переполнение вместимости или посторонний инвариант не считаются обнаружением намеренно внесённой ошибки.

Проверка устроена как цепочка переводов между представлениями, а не как один магический checker. Намеренно изменённая модель показывает, способен ли неизменённый checker заметить конкретное ослабление семантики. Сценарий исполнения создаёт наблюдаемую историю. Нормализатор удаляет только детали представления — временные метки или конкретные UUID — но обязан сохранить равенство идентичности, причинности, порядка и границ фиксации. Затем проверка соответствия определяет, можно ли сопоставить каждую наблюдаемую границу исполнения допустимому фрагменту переходов модели, не дорисовывая отсутствующие факты.

Если хотя бы один перевод теряет существенное различие, хороший результат становится недействительным. Схлопнуть две физические попытки в одну — значит спрятать окно аварийного завершения. Заменить разные `operation_id` абстрактным «какой-то идентификатор» — значит удалить инвариант повторной попытки. Считать отсутствие результата отказом — значит выдумать наблюдение, которого нет в истории. Поэтому абстракция здесь полезна только пока она сокращает представление, но не сокращает семантику.

Доказательная база разделена по силе утверждения:

```text
Тесты реализации
  Выбранные пути реализации на Python прошли.

Ограниченная конечная модель
  В заявленной конечной области нарушение не найдено.

Проверенный индуктивный инвариант
  Проверен инвариант конечной абстракции.

Соответствие сценария исполнения
  Наблюдавшаяся трасса соответствует переходам модели.

Обязательства интерфейсов
  Проверены локальные предположения поставщика и потребителя.

Безопасность
  Не устанавливает безусловную живучесть.
```

## Что реализовано в Agentlog 0.3

Одна система переходов получила несколько исполняемых проекций и связанную модель идентичности артефактов:

- причинная история хранит зафиксированные запросы и наблюдения;
- `DurableModelLoop` реализует протокол предложения, проверки и внешнего действия;
- промежуточные обработчики меняют содержимое, сохраняя идентичность;
- инструкции канонизируют запрос до фиксации;
- артефакты фиксируют идентичность содержимого результата;
- `Sequence` композирует ту же границу через дочерние запуски;
- FastAPI предоставляет транспорт команд и наблюдений;
- SSE и причинная трасса являются проекциями истории;
- SQLite реализует сохраняемую историю и контрольную точку;
- детерминированная лаборатория контроля качества проверяет сквозной сценарий;
- поставщик Ollama проверяет отдельную границу интеграции с настоящей моделью.

Ядро среды исполнения не имеет обязательных сторонних зависимостей. FastAPI,
Ollama и MCP Streamable HTTP client устанавливаются как необязательные
дополнения; лаборатория MCP/MinIO использует отдельное локальное окружение.

## Итог

Вместо набора слабо связанных объяснений остаётся один переход:

```text
предложение
→ проверка допустимости
→ зафиксированный запрос
→ внешнее действие
→ зафиксированное наблюдение
→ состояние
```

Языковая модель, инструмент и дочерний запуск занимают разные типизированные позиции в этой системе. Артефакт присоединяется к ней как отдельная модель идентичности результата. Окно аварийного завершения, идентичность повторной попытки, память протокола и причинная история уже не выглядят дополнительными возможностями: они следуют из границы между внешним эффектом и зафиксированным наблюдением.

Среда исполнения не делает ненадёжный компонент правильным. Она ограничивает пространство допустимых переходов, делает явной границу внешнего эффекта и сохраняет проверяемое происхождение принятого состояния.

Большая языковая модель — новый компонент.

Задача построения управляемой системы вокруг ненадёжного компонента — старая.
